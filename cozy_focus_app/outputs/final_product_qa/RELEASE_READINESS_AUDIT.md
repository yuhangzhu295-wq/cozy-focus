## C1 · Android release signing — **still blocked, and deliberately not unblocked**

**Measured.** `android/key.properties` does not exist. `android/app/build.gradle.kts`
reads it at line 10 and switches on `hasReleaseSigning` (line 65), so the release
build falls back to `signingConfigs.getByName("debug")` — a build that succeeds and
an AAB that is signed with the debug key.

**What I did not do.** I did not generate a keystore. The signing key *is* the
app's permanent identity: whatever key is used for the first Play upload is the
only key that can ever update that listing. Generating one here would bind that
identity to a key I invented, with a password I would then have to hand over
through this transcript — which is not "secure storage" in any sense the brief
means, and would be an irreversible decision made on the owner's behalf.

**What is already in place, and proven rather than assumed.** `.gitignore`
protects the key in both places it could leak:

```
cozy_focus_app/android/.gitignore:12:key.properties
cozy_focus_app/android/.gitignore:14:**/*.jks
```

Proven by creating a real `android/key.properties` and `android/probe.jks`:
`git status` showed neither, and `git check-ignore -v` named both rules. The probe
files were then deleted. `git log --all -- "*.jks" "*.keystore" "key.properties"`
is empty, so no key material has ever been committed.

**The owner's step, when ready.** Nothing in the code needs to change — the build
switches over the moment the file exists:

```
keytool -genkeypair -v -keystore ~/cozyfocus-release.jks \\
  -keyalg RSA -keysize 2048 -validity 10000 -alias cozyfocus
```

then `android/key.properties` with `storeFile` / `storePassword` / `keyAlias` /
`keyPassword`, the keystore stored outside the repository, and both backed up
somewhere that is not this machine.

## C2 · Launcher icon — **candidate produced, not approved, nothing replaced**

**Measured.** `mipmap-xxxhdpi/ic_launcher.png` is 192×192 and its three dominant
colours are `#000000` (24 668 px), `#54C5F8` (8 407 px) and `#01579B` — Flutter's
own light and dark blue. It is the stock Flutter logo.

**Candidate:** `outputs/launcher_icon_candidate/` — six PNGs (48/72/96/144/192/512)
generated by `tools/qa/make_launcher_icon.py`, which draws the companion's own
silhouette: floppy ears, the closed happy eyes it wears everywhere else in the
app, and the two-leaf sprout. Original, drawn from the app's own palette, no
third-party asset.

**The first draft failed and the failure is recorded in the script.** It drew the
head as one white ellipse with a crescent of shade, which at 48dp is a featureless
blob with a bite out of it — it read as a broken egg. The contact sheet
(`ICON_SIZES_contact_sheet.png`) shows every size at true pixels, which is how the
failure was caught: a 512px render looks fine and a 48px one does not.

**Not marked as passing.** Nothing under `android/` was touched, the shipped icon
is still the stock logo, and the gate still reports `LAUNCHER_ICON` as BLOCKED.

## C3 · System notifications — **not implemented, and one screen was lying about it**

**Measured.** `flutter_local_notifications: ^18.0.1` is in `pubspec.yaml`, and
`grep -rn "flutter_local_notifications\\|FlutterLocalNotifications" lib/` returns
**0**. `git log -S "FlutterLocalNotifications" -- lib/` is empty, so it has never
been imported.

**The settings page and the notifications page are honest** — they say
`当前版本尚未接入系统通知` and `不可配置`.

**The focus setup page was not.** It carried `专注结束提醒` with a real `Switch`,
wired to a working `setState`, **defaulting to ON**, backed by a local `bool` that
never left the page. The switch moved, so the user got positive feedback that
reminders were armed, and nothing could be scheduled. That is worse than a dead
row: a dead row is merely inert.

**Fixed.** The switch and the field behind it are gone; the row now states the
same thing the settings page states. Guard:
`test/presentation/focus_setup_honest_rows_test.dart` asserts this screen presents
**no toggle at all** and carries both honest lines. Reverse-proved: restoring the
switch and a fake chevron fails three of its four cases.

## C4 · White noise — **not implemented; the setup page invented a value for it**

**Measured.** No audio package in `pubspec.yaml` (`audioplayers` / `just_audio`:
0 matches). **0** audio files anywhere under `assets/`.

**The focus control row is honest** — the board draws four controls, the app draws
three, and the omission is documented in `focus_control_row.dart`.

**The focus setup page was not.** It showed `专注白噪音` with `森林  >` — a
*current value* and a *drill-in chevron* for a picker that does not exist, on a row
with no `onTap`. It promised both a setting and a navigation. The project had
already refused to add exactly this shape as `更多 ›`.

**Fixed.** The chevron and the invented `森林` are gone; the row states that the
version has no audio. Same guard and same reverse proof as C3.

**Neither feature was implemented.** The brief is explicit that a design board
showing a switch is not a reason to declare a feature done, and neither of these
is done.

## C5 · Data export and restore — **absent, and not invented**

**Measured.** The data-and-sync page contains exactly one action: a back button.
There is no export, no import, no backup and no restore anywhere in `lib/`. The
only "export" in the repository is `WrappedExportService`, which captures a widget
subtree to a PNG for the share card — an image export, not a data export.

**Not fixed, deliberately.** Local export/restore is a **new feature**, and the
brief forbids inventing features. It also needs product decisions that are not
mine: the file format, where the file goes, and above all what restore *means*
(overwrite everything? merge? what happens to a record that exists in both?).

**What the app does say, honestly:** the page states that data is saved locally
and that cloud sync is unavailable. It does not claim a backup exists. That is the
correct state for V1 as decided in D7 — but it is worth the owner knowing that
uninstalling the app currently loses everything.

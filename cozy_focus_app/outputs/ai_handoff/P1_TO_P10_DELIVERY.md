## 一、这份交付是什么

把开发包 v2 的 16 张设计图，在**现有架构上增量实现**成可运行、可持久化、可重启的功能，而不是另起一套页面。

- 底部导航仍是 **首页 / 记录 / 成长** 三个一级 Tab（未改成 5 个）。
- 专注流程仍复用 `/focus/setup → active → complete → save → reward`，没有第二套 Focus Engine。
- 宠物仍走 `CompanionContext → CompanionBehaviorDirector → CompanionAnimationController → CompanionSpritePlayer`，动画层未改。
- 所有新数据都进现有 SQLite（schema 从 v4 升到 **v11**），每一步都有迁移测试。

## 三、8 个新功能的闭环

1. **任务域**：任务 / 子任务 / 分类 / 预估时长，真实读写。
2. **今日计划**：`task_schedules`，一天一条、唯一约束、级联删除；「今天」筛选是真实查询。
3. **专注计时模式**：`FocusTimingMode`（countdown / countUp / deepFocus）与 `FocusMode` 分开；深度专注由引擎拒绝暂停，不只是隐藏按钮。
4. **分心收集箱**：专注中速记，不打断计时（有测试断言 elapsed 不变、没有写入暂停区间）。
5. **专注复盘**：心情四个值（**无默认选中**）、收获标签、下次继续；旧 emoji 迁移为 id。
6. **时间线**：只读投影，**不新建事实表**，从 `task_schedules` / `focus_records` / `distraction_notes` / `rest_sessions` 聚合。
7. **统计分析**：总时长 / 次数 / 平均时长 / 每日柱状 / 任务分布，全部由记录算出，**没有任何设计稿示例数字被硬编码**。
8. **自由时间**：`rest_sessions` 独立事实表，休息不计入专注统计；宠物进入 `sleep`。

## 六、测试期间发现并修掉的真实缺陷

这些都不是「测试写错了」，是代码错了，每条都配了回归测试：

1. **`AnalyticsRange` 没有值相等** → 作为 Riverpod family key 每次重建都是新的窗口，统计页永远停在加载态，而代码看起来完全正确。
2. **下拉刷新只刷新了计划** → 时间线与统计是投影，没有 controller 可 reload，用户下拉后数字不变。
3. **计划空状态遮住了时间线** → 没有安排的那一天切到「时间线」显示的是「今天还没有安排」，时间线 Tab 根本进不去。
4. **「下一个任务」卡片出现在时间线上** → 设计里时间线没有这张卡；P2 那个本该覆盖它的测试两种布局都能通过，是假绿。
5. **`FocusSession.elapsedSecondsAt` 在时钟倒退时抛异常** → `clamp(0, raw)` 上下界颠倒，NTP 校正 / 改时区 / 用户改设备时间都会让 1 秒的显示 ticker 抛错。
6. **`DriftRestDao.update` 覆盖了 `DatabaseAccessor.update`** → 同类里所有 `update(table)` 变成类型错误。
7. **宠物状态覆盖丢掉了 craft** → 第一版 P9 覆盖只返回 idle/focus/pause/sleep，把 avatar 自己推导的 craft 状态吃掉了，5 个既有测试失败；改成只回答 avatar 看不到的「是否在休息」。
8. **`TextEditingController` 在对话框还在退场时被 dispose** → 自定义时长弹窗抛「used after being disposed」。
9. **长文本按 code unit 截断会切断代理对** → 改成按 code point 截断，并加了 emoji 用例。

## 八、模拟器实机走查（2026-10-07 补做）

P1–P10 交付后，把 debug APK 装到 Pixel 7 / API 34 模拟器上，逐屏走查了：
记录域入口、今日计划三个视图（计划 / 时间线 / 统计）、任务列表空状态、新建任务、
专注设置、专注进行页、分心收集箱浮层、专注完成页、分心箱清单、休息页、设置页。

**走查抓到 3 个全套测试都没抓到的真实缺陷**，全部已修并配反向证明过的回归测试：

1. **专注设置页底部导航高亮的是「成长」**。这个流程从首页进入，同一流程的下一屏
   `focus_complete_page` 标的是「首页」。没有任何测试断言过导航高亮的是哪个 tab，
   只断言过导航存在。定位方式是读像素：设置页的「成长」标签用 `primarySage` 画，
   首页的「首页」标签也是 —— 源码里不该有的矛盾。
2. **记录页的分心箱计数在速记之后不刷新**，一直显示「还没有记录」，而分心箱里其实
   已经有那条笔记。计数来自一个 `FutureProvider`，答案被缓存到它被销毁为止。
   第一版修法（每次收件箱变动就 invalidate）弄坏了两条 controller 级测试——invalidate
   会排一个 Riverpod 任务，测试在同一 tick 结束就留下 pending timer。改成从收件箱
   controller 自身状态派生：单一真相来源、不排任务、还少一次查询。
3. **休息页四个时长排成 3+1**，设计稿是 2×2。`Wrap` 把 30 分钟单独挤到第二行，
   读起来像「列表 + 一个补充项」而不是四个等权选择。控件都在、都能点，正是休息页
   测试唯一检查的东西。
4. **安排到今日计划对「已经安排过」的任务静默失效**。任务已在今天 22:00，表单却
   给出全新的 23:30，按下「添加到今日计划」什么都不写 —— `place` 是幂等的，对
   当天已有的任务直接返回原行并丢弃传入的时间与时长，用户看不到任何反馈。
   现在表单读回那条安排、预填它的时间与时长、说明「保存后会更新原来的时间」，
   按钮变成「更新计划」，保存走更新而不是新增。

   顺带记一笔：这个修复的第一版让 `updatePlacement` 去 controller 已加载的当天列表里
   找那一行，列表没加载完时就什么都不做 —— 同一个失效模式换了个地方。测试抓住了。
   另外为了防「查询返回时覆盖用户刚点的时长」加了一个 `_touched` 守卫，但我**写不出
   会因它而失败的测试**（每次尝试都落在查询之后），所以守卫保留、并在守卫处写明
   它没有测试覆盖，而不是留一条怎么都绿的测试。

每个修复都有测试，且每个测试都做了反向证明：把修复还原，测试就红。计数的那个变异
用 `read` 替 `watch` —— 原始缺陷的同一个机制 —— 失败症状与线上一致。

修复后在模拟器上复验：记录页显示「1 条待处理」、休息时长是 2×2、专注设置页高亮
「首页」。

### 修掉的五个

**1. 倒计时超时把超出的时间当专注时间入账（`6c66fe6`）**

设备上一条 25 分钟计划、`countdown` 的会话，因为 App 被杀掉而跑了 94 分钟，回来时完成页
写着「本次专注时长 **94:30**」、奖励 **+188 币 / +470 XP**——94×2 与 94×5，一分不差地
按 94 分钟发的。`complete()` 用「发现它的那个时钟」盖 `endAt`，而不是用目标达成的那一刻。

倒计时的契约是「到点就结束」，App 活着的时候 ticker 也确实在到点后一秒内结束它；超时只
存在于没人看着的时候。所以现在 `endAt` 由起点、目标和暂停反推，记录长度不再取决于 App 当时
是否活着。早于目标手动结束的会话保留真实时长，正计时/深度专注不受影响。

5 条测试，去掉 clamp 有 3 条会红。设备复验：新开 5 分钟倒计时、立刻强杀、8 分钟后重启，
记录 `duration_seconds = 300`、`start 09:57:34 → end 10:02:34`、奖励 +10/+25。

**2. 倒计时在输入时到期，用户正在写的那条想法被丢掉（`6665e3b`）**

完成跳转是 `go`，会替换整条路由栈，把「记一下」的底部面板一起带走。设备上实测：输入到
一半计时器到点，面板消失，那条笔记**从未出现在分心箱里**。而面板存在的理由就是「捕捉想法
不该花掉专注时间」——会话结束也不该花掉这条想法。

现在完成跳转等面板关掉；无论用户是保存还是关闭，跳转都不丢。3 条 widget 测试，去掉守卫
3 条全红。

**3. 保存到相册的卡片叫 `..._wrapped.png.png`（`17579d7`）**

`gal` 自己会补扩展名，它的文档明确写着「Do not include the extension」。调用方传了带 `.png`
的名字，于是 `Pictures/` 里躺着 `cozy_focus_2026_wrapped.png.png`。提示条说保存成功了，
只有去列目录才看得见。扩展名现在由服务自己管：相册名去掉扩展名，分享用的临时文件补上。
4 条纯函数测试，去掉 strip 有 2 条红；设备复验后新文件是 `cozy_focus_2026_wrapped.png`。

**4. 记录行印的是心情的存储 id，奖励条把宠物叫「Pet」（`17b3bab`）**

今日记录的行写 `Text(r.mood!)`，所以复盘选了「心流」的记录，在列表里显示字符串 **`flow`**。
`FocusMood.face` 的存在理由就是「复盘页、记录详情页和任何后续摘要都画同一张脸」——这一行

## 十四、第三轮：小屏与横屏，四处修复

起点 `b938d29`，代码终点 `924fa93`（本节的文档提交在其之后）。测试从 1876 涨到 1893。这一轮换了模拟器的尺寸和方向来走，
所以抓到的都是「一种屏幕尺寸下永远看不见」的问题——全套测试一直只在一个尺寸上跑。

方法：`adb shell wm size 720x1280` + `wm density 320`（360dp 宽的小屏），
以及 `settings put system user_rotation 1`（横屏，先 `wm size reset` 回真机的 411×914dp）。

**1. 月报趋势图的日期标签被截成一位数字（`monthly_report_page.dart`）**

横轴是 31 个 `Expanded` 列，360dp 下每列只有约 7dp，而 8px 字号的双位标签需要约 9dp。
`Text` 默认 `clip`，于是 `14 / 21 / 28` 被画成一位数字加一条竖边——一眼读过去横轴是
1、7、1|、2|、2|。411dp 下每列 8.9dp 刚好放得下，所以只有小屏才出问题。

修法：把标签放进 `OverflowBox(maxWidth: 40, maxHeight: 20, fit: deferToChild)`，让它按自身宽度
排布。`fit` 必须是 `deferToChild`：默认的 `max` 会向父级要尽可能大的高度，而 Column 给非弹性
子节点的是无界主轴，直接抛断言——这一步我先写错了一次。

**2. 年报三张统计卡的标签和数值行被省略号截断（`yearly_report_page.dart`）**

同样是 360dp：卡片约 100dp 宽，`年度专注时长` 放不下，行里显示成 `年度专注时…`；
`比去年多了 100% ↑` 连箭头一起被截掉。截断的词不是更短的词。

修法：标签和数值行都放到两行，三张卡用 `IntrinsicHeight` + `CrossAxisAlignment.stretch` 拉成
等高（否则换行的卡会比其他卡高）。411dp 下每行仍然只占一行，**设计稿尺寸上的排布一点没变**。

**3. 年报热力图卡片表头溢出 0.75px（`yearly_report_page.dart`）**

`spaceBetween` 的 Row 里两个 Text 加起来比 360dp 的卡片宽 0.75px——debug 下是一条黄黑条纹，
release 下是被静默裁掉的说明文字。这条是**新写的测试在 360dp 下 pump 时自己抛出来的**，不是我看
出来的。修法：把说明文字改成 `Flexible`，让它换行而不是把标题挤出边界。

**4. 横屏下报告页被拉满整屏（`app_theme.dart` + 三个报告页）**

App 没有锁定方向——manifest 和 `SystemChrome` 里都没有，所以横屏是真机可达状态。914dp 宽下，
年报热力图 `spaceBetween` 的 31 个固定尺寸日格被摊到间隔 21dp，日历彻底读不出来；所有卡片都
变成信箱比例。

修法：新增 `AppLayout.reportMaxWidth = 560` 和 `reportGutter(screenWidth)`，三个报告页把它用作
滚动视图的水平内边距，内容于是收窄并居中。用 `max(20, (w-560)/2)` 而不是分支，两种情形在
`w = 600` 处平滑相接、没有台阶。**竖屏 411dp 下这个上限不生效**，所以设计稿的排布不变。

像素复核：横屏内容 557dp（≈560），热力图日格间隔从 21dp 降到 9.2dp，日历恢复可读。
左侧边距比右侧多 52dp 是 App 窗口相对屏幕的偏移（`mAppBounds` 的挖孔内边距），**内容在窗口内
是居中的**——这一点我差点读成「没居中」。

## 十五、第四轮：P32 §31A 复现到根因，两个取整走错的成员归位

起点 `c4dd289`，测试从 1893 涨到 1898。这一轮做的是项目自己 `owner_decisions_required` 里
那条写着「先复现确切原因」的：**一条显示"已经专注了 30 分钟"的会话结算成 29:55，差 5 秒不到
地毯的 1800 秒配方**，于是制作卡在 29/30，玩家以为自己达标了。

### 确切原因

**不在结算里。** 结算一直是精确的：1795 秒进、1795 秒出，`RewardService` 按
`(elapsed / 60).floor()` 付 29 分钟的币。原因在**同一个屏幕上把同一个数量按两个方向取整**：

- 运行页自己的「已专注」标签：`(elapsedSeconds / 60).floor()` → 29 分钟
- 提前结束弹窗：`(elapsedSeconds / 60).ceil()` → 30 分钟

于是弹窗承诺了用户没有专注完的一整分钟，而它身后的屏幕写着另一个数。完成页的 29:55、币数、
制作门槛全都用真实秒数——**弹窗是唯一说错的**。

复现（改之前跑的）：1795 秒渲染出「已经专注了 **30** 分钟，…」，59 秒渲染出「已经专注了
**1** 分钟，…」。改成 `~/ 60` 后分别变成 29 和 0，两条测试守着。

### 顺藤摸出来的第二个：同一条记录，两个时长

跟着同一条线索查下去（项目自己的教训：第二个缺陷常藏在第一个修复的输出里），记录行也在自己
算一套：`progress_overview_page.dart` 里 `(r.durationSeconds / 60).floor()`，而
`formatDurationText` 是工程里写明「第二个格式化器就是对'一小时是什么'的第二个答案」的唯一
裁决者，时间线和两个报告页都读它。于是同一条 54 秒的记录，记录行读 `0 分钟`、时间线读
`1 分钟`；1795 秒的记录读 `29 分钟` 与 `30 分钟`。

修法是让记录行读那个共享格式化器。**注意这条不能反过来修**：`formatDurationText` 用 `round`，
时间线、报告页、任务页都依赖它，把 54 秒改成 `0 分钟` 只会把矛盾搬到更多地方。

### 两个取整族，以及它们为什么不同

两个修复各自把一个走错族的成员送回去，而不是把所有东西统一成一个取整：

- **进度族（floor）**：`RewardService` 的分钟数、制作进度、「已专注」标签、提前结束弹窗。
  回答「你完成了几整分钟」，是用户拿去和**目标或报酬**比对的数，**绝不能多报**。
- **时长标签族（round）**：`formatDurationText` → 时间线、报告页、任务时长。回答「这一段有多
  长」，是**描述**，按四舍五入写才自然。

设备上的证据（新开一段 152 秒的会话）：弹窗按进度族说 1 分钟（打开那一刻的快照），完成页写
`02:32`，奖励 `+4 币 / +10 XP`（floor 2 分钟），记录行按标签族写 `3 分钟`，与时间线一致。
两族各自自洽；跨族的数字本来就回答不同的问题。

### 仍然留给你的

配方门槛本身没有动：**1800 秒的配方是否该接受 1795 秒的专注**，仍然是
`owner_decisions_required` 里的原问题（"elapsed truth 还是 planned-duration grace"）。这一轮
修掉的是「应用告诉用户做了 30 分钟、然后只按 29 分钟结算」——那不是取舍，是自相矛盾。

### 一处我自己的测量错误，第二次犯

我一度把设备上那条 02:36–02:37 的记录当成 54 秒（"所以它显示 1 分钟是 bug"）。设备时区是
**UTC**（`date +%z` = +0000），我却是按宿主机时区换算的——和第三轮周报那次同一个错误。
按 UTC 重算：那条是 **84 秒**，floor 和 round 都是 1 分钟，**两种取整都解释得通，它不是证据**。
真正的证据是 54 秒那条（UTC 16:12），而它不在今天的列表里。**下结论前先用 `date +%z` 把时区
钉死**，别再拿墙上时钟推断。

## 十六、第五轮：可访问性扫描（25+4 个按钮没有名字）

起点 `6fb07f1`，测试从 1898 涨到 1913。这一轮做的是 `next_action` 里点名的第二件可独立完成的
事：「新屏幕的触控尺寸与语义覆盖扫描」。

### 找到什么

`lib/presentation` 里有 **25 个 `IconButton` 没有任何可访问名字**——没有 `tooltip`，也没有
`Semantics` 包装。返回箭头、报告页的上下周期箭头、复盘页的关闭、分享按钮。读屏器只会念
"按钮"，然后停住。没有任何测试发现，因为**从来没有任何测试问过一个控件叫什么**。

### 正确的修法不是显而易见的那个（三种都实测过）

我先用了工程里已有的形状，然后按语义树量了结果：

| 写法 | 语义树结果 |
|---|---|
| `Semantics(button: true, label: '返回', child: IconButton(...))` | **两个** button 节点：包装那个有名字，IconButton 自己那个**没有**。读屏器两个都会遇到。 |
| `IconButton(tooltip: '返回')` | 一个节点，但字符串落在节点的 `tooltip` 字段上，`label` 仍是空。 |
| `IconButton(icon: Icon(Icons.arrow_back, semanticLabel: '返回'))` | **一个**节点，带名字。 |

所以最终用的是第三种，给图标的 `semanticLabel`。**工程里原有的 4 处 `Semantics` 包装（统计视图
的上下段、时间线的停止按钮、捕捉面板的关闭）有同样的双节点问题**，也一并改掉了——它们的 key
移到 `IconButton` 上，测试照旧。

另外发现同一类的第二个来源：**`PopupMenuButton(tooltip:)` 的 tooltip 落在 Tooltip 节点上，按钮
节点仍然无名**。4 处（分心箱的 ⋯、伙伴选择卡的 ⋯、任务详情的 ⋯、记录行的 ⋯）都补了图标
`semanticLabel`；记录行那个按分心箱的先例带上行名，读屏器能听出是哪一行。

### 守卫怎么写的，以及为什么这样写

`test/architecture/control_accessibility_test.dart` **遍历 `rootSemanticsNode`**，断言没有任何
带 `isButton` 的节点 label 为空。不按控件查语义——那样恰恰会漏掉最要命的情形：**控件包了，
它产生的节点没包**。两个反向证明守着这条：一个裸 `IconButton` 必须被报出来；一个只有
`Semantics` 包装的必须**仍被报出来**（证明读树而不是读控件是必要的）。

**尺寸部分只记录、不断言**：多处控件是 38–46dp，低于 48dp 指南，但那是本 App 的密度而不是
缺陷——Material 自己的 `Chip` 高 32dp、`SegmentedButton` 高 40dp，本 App 的分段控件与筛选
chip 与之一致。按 48 断言会判设计自己的组件不合格，按 38 断言则把今天的现状固化成规则。

`tools/find_unlabelled_icon_buttons.py` 对全工程做静态扫描，覆盖测试挂不起来的屏幕。

### 设备验证

读的不是截图，是 **Android 无障碍树**（`uiautomator`/UI 工具给出的 `content-desc`，也就是
TalkBack 读的字段）。周报页现在：返回按钮 `"返回"`、左箭头 `"上一周"`、右箭头 `"下一周"`。

### 顺带修掉的一处数据不一致

`assets/companions/rabbit/manifest.json`（运行时清单）写 `groundBaseline: 459`，而同一个包的
`animation_manifest.json`（创作契约）写 458、几何审计实测帧也在 458。没有任何测试把这两份
清单互相对照过。改 458 时被「镜像与 JSON 逐字段一致」那条测试拦下——**459 还存在于一份 Dart
镜像里**（`companion_action_manifest_data.dart`，由 `tools/gen_manifest_dart.py` 生成）。用生成器

## 十七、第六轮：清 open findings —— 关掉一条、修掉一条、撤掉两条

起点 `e1a070e`，测试从 1913 涨到 1916。这一轮逐条处理清单里剩下的 open findings，其中两条

### 关掉：符号链接的拒绝只在校验策略层测过

清单原文：「symlink rejection is NOT verified through the reader」。测试文件里也写着同样的
话：「读取器是否真能识别符号链接，取决于解码器，这个测试够不到——是一条未验证项，不是通过。」

现在关了。`ZipEncoder` 写死了 MS-DOS creator，而解码器只有在 `versionMadeBy >> 8 == 3` 时
才会去读 Unix mode 的 file type 位，所以**编码器造不出这种条目**——于是手工补字节：用
`ArchiveFile.mode = 0xa1ff`（S_IFLNK | 0777）让编码器把模式写进外部属性，再把中央目录记录
的 creator 字节补成 3。

测试先断言**这个输入确实是符号链接**（`ZipDecoder` 解回来 `isSymbolicLink == true`、
`symbolicLink == '/etc/passwd'`），再断言读取器拒它（`non_regular_entry`）。第一步不能省：
拒绝一个从来就不是符号链接的东西会「因为错误的原因通过」。另加一条对照——同样字节的普通
文件必须被接受，否则「全都拒」也能让上面那条绿。

反向证明：让读取器忽略 `isSymbolicLink`，这条立刻红。

**结论：读取器是对的**，这条是验证缺口，不是缺陷。

`furniture_use_panel.dart` 的 `_activityLabel` 只要动作**存在**就打印「咪咪 正在坐下」。
但 `room_sit` 在任何包里都没有帧——三层都回退到 idle，狗的分层骨架只把 `earRotation` 转了
0.06——**画出来是一只站着的宠物**。

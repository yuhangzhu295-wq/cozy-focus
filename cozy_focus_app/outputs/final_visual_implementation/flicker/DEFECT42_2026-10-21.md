# Defect 42 — companion blanks for a frame when its action changes

## State on the dev branch

`recovery/v4.2.1-rebuild` at `8ae9035` **already contains the fix**
`c89076b` (2026-10-12). The report the brief quotes (`04647b3`) is the commit
that *recorded* the defect, before the fix.

The fix, in `lib/presentation/companion/mochi_visual_provider.dart`:

- The hero draws the layered rig for `idle` and a sprite for every other pose,
  so the first tap builds a new sprite element. A new element has no decoded
  image, and `gaplessPlayback` has nothing to hold.
- `interactionSpriteSpecs()` returns `tap_react` and `pet_react`, and
  `_SpritePrecache` decodes them while the rig is still on screen.

## Device runs on the fixed build (2026-10-21)

Installed from `flutter build apk --debug` at `8ae9035`, force-stopped and cold
started before each run. The instrument now reads the recording's own frame
timestamps; `--fps` only changes how many samples ffmpeg takes, so the numbers
below are split into samples and recorded frames.

| run | samples | recorded frames | median / max frame gap | result |
|---|---|---|---|---|
| cold start, 1 tap | 194 @ 20fps | 93 over 9.94s | 100 / 234 ms | ink median 5625, min 4141, **0 dips** |
| cold start, 2 taps | 274 @ 20fps | 103 over 13.89s | 134 / 336 ms | ink median 5620, min 4148, **0 dips** |
| control: tab 记录 | 96 @ 20fps | 41 over 5.06s | 117 / 484 ms | ink falls to 0 and stays there, **0 flicker** |

The control is the instrument's own negative case: switching to a page with no
companion drops the ink to zero for the rest of the window, and the classifier
must *not* call that a flicker. It reports `dip_frames: [91..94]` and
`flicker_frames: []`.

**What a clean run means.** The device recorded about 10 frames a second
(median gap 100-134 ms), so the result is "no blank lasting one recorded
interval (~100 ms) or longer". A 50 ms blank could fall between recorded
frames and is **not** excluded by these runs. The earlier "60 fps" run claimed
a stricter measurement; it did not have one, because `-vf fps=60` duplicates
the ~10fps recording. That claim has been removed.

## Reverse proof

1. **Unit guard** — `interactionSpriteSpecs()` temporarily returned `const []`:
   `mochi_interaction_precache_test.dart` failed with
   `Expected: non-empty / Actual: []` and
   `Expected: contains all ... ['tap_react', 'pet_react'] / Actual: []`.
   Restored: 3/3 pass.
2. **Device** — the same empty list was built and installed, the app was
   force-stopped and cold-started, and the detector was run. **It still
   reported 0 dips.** The original blank is not reproducible on this
   host/build; the frames decode fast enough that no recorded frame is blank.
   Recorded as `DEVICE_REVERSE_PROOF = NOT_REPRODUCED`, not as a pass.

## Instrument changes in this round

- `classify_flicker()` replaces the old "interior dip" test: a low run counts
  only when it is at most 3 samples **and** has ink before and after. Longer
  absences are page changes.
- `--selftest` runs seven cases: one, two and three blank frames are flickers;
  four blank frames, a page round-trip, a permanent absence and no dip are not.
  All seven pass. The classifier can be shown to fail.
- `raw_video_meta()` writes `raw_frames`, `raw_duration_s`, `raw_max_gap_s` and
  `raw_median_gap_s` into every report, and the note states that
  `extract_fps` is a sampling rate, not a device rate.

## What this means

- The root cause and the fix are the ones established in `c89076b`; the code is
  present and the unit guard is the regression proof.
- The device instrument passes on the fixed build, cold and warm, one and two
  taps, at its real resolution of ~100 ms.
- The device-level reverse proof **could not be made to fail** on this host, so
  it is not evidence that the fix is what makes the run pass.
  `DEVICE_REVERSE_PROOF = NOT_REPRODUCED`.
